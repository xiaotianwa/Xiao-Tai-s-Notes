## 二、执行经验总结

### 1. 不要先大范围重构 UI，再回头判断功能

历史问题：

- 多次要求“完全重构 UI”“一比一复刻”后，实际出现“你一直都没有实现 UI 重构”“页面只写了 UI 没有实际效果”“按钮和标题重合”“底部被遮挡”等反馈。
- 大范围同时改首页、日记、纪念日、提醒、记账、音乐、备忘、设置、漫画，容易导致控件存在但业务未接入。

正确方式：

- 按页面逐个闭环：先看参考图，再读现有页面代码，再列控件到功能映射，再改代码。
- 每个控件必须归类为 `已接入`、`本地可用`、`后端待接入`、`明确不做`。
- 不能接入的控件要写进对应 UI contract 或未实现清单，不要让 UI 看起来已经可用。

教训：

- 对这个项目，UI 复刻不是“画得像”就结束。用户更关注“看起来可点击的地方是否真的有效”。

### 2. 任何“预留接口”都必须有记录

历史问题：

- 用户多次要求“未实现的功能预留接口并记录”。
- 后续审查发现音乐、情侣事项、本周目标、备忘、设置仍有 `_showReserved...`、正文标记、placeholder 行为。

正确方式：

- 代码中出现 `Reserved`、`placeholder://`、`暂未开放`、正文标记字段时，必须同步记录到文档。
- 记录应包含：控件位置、当前行为、缺的模型/API、建议实现顺序。

教训：

- “先预留后补”可以接受，但不能无痕预留。无记录的预留会被用户视为假完成。

### 3. 真机联调前必须确认 API 基址和网络路径

历史问题：

- 多次出现“连接服务器超时”“我的 API 接口为 https://api.xthblog.site/v1”“真机联调用的是局域网，不是服务器”。
- Android 模拟器 `10.0.2.2`、真机局域网 IP、线上域名 `/api/v1` 和用户给出的 `/v1` 曾混用。

正确方式：

- 联调前明确目标：本机后端、局域网后端、线上 API。
- 用户当前明确的服务器接口根地址为 `https://api.xthblog.site/`；后续本项目 App 真机/模拟器联调默认优先使用该线上服务器，不要再习惯性使用 `10.0.2.2:3100` 或本机默认地址。
- Flutter 的 `XIAOTAI_API_BASE_URL` 需要传完整 API base；若代码接口仍以 `/api/v1` 为前缀，运行时应显式传 `https://api.xthblog.site/api/v1`，不要把服务器根地址、`/api/v1` 和 `/v1` 混用。
- Flutter 运行必须显式带 `--dart-define=XIAOTAI_API_BASE_URL=...`。
- 先在设备侧验证 `/health` 或一个公开接口，再安装/调试 App。

教训：

- 不要根据默认值猜测网络。真机、模拟器、浏览器和线上部署是四个不同路径。

### 4. Windows PowerShell 要按兼容语法执行

历史问题：

- 使用 `??` 导致 PowerShell 解析失败。
- `foreach { } | Format-Table` 这类写法在当前环境失败。
- 正则转义多写一层导致 `rg` 不命中或报错。

正确方式：

- 默认按 Windows PowerShell 5.1 兼容写法处理。
- 不使用 `??`、复杂一行式和脆弱转义。
- 中文输出前设置 UTF-8：`$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)`。

教训：

- 本项目在 Windows 桌面环境下开发，脚本稳定性比写法简洁更重要。

### 5. 后台服务启动要避免端口冲突和假启动

历史问题：

- 曾出现 `EADDRINUSE`、启动命令超时、端口未监听、`Start-Process` 环境变量冲突。

正确方式：

- 启动前查端口占用。
- 后台进程输出重定向到明确日志文件。
- 启动后检查端口和健康接口，而不是只看命令是否返回。

教训：

- “服务启动了”必须由健康检查证明。

### 6. 远程部署和删除必须先备份、再定位、最后执行

历史问题：

- 用户多次担心服务器文件被删、数据库被覆盖、COS 数据还在但 App 数据不见、宝塔目录看不到项目。
- 历史操作涉及清理服务器无用文件夹、删除图片目录、迁移 COS，风险较高。

正确方式：

- 先列目录和环境变量，确认真实路径。
- 数据库、上传目录、COS 对象执行前先备份或 dry-run。
- 删除操作必须限定绝对路径，不能用模糊匹配。
- 任何涉及生产数据的命令都要说明目标和保留内容。

教训：

- 用户非常重视数据不丢失。部署效率不能高于数据安全。

### 7. 密钥不能通过对话长期流转

历史问题：

- 会话里出现过私钥、COS Secret、服务器密码、AI Key。

正确方式：

- 后续只让用户写入 `.env`、宝塔环境变量或本机临时文件。
- 回答中只引用变量名，不引用值。
- 发现密钥已进入会话，应提醒轮换。

教训：

- 私有项目不等于可以放松安全。聊天记录本身就是长期留存面。

### 8. Flutter 格式化和测试要处理本机 telemetry 权限问题

历史问题：

- `dart format` 实际格式化了文件，但因 `C:\Users\17265\AppData\Roaming\.dart-tool\dart-flutter-telemetry-session.json` 权限问题返回非零。
- Widget 测试多次暴露 RenderFlex overflow、无限宽约束、pending timers。

正确方式：

- 格式化/测试前可设置 `DART_SUPPRESS_ANALYTICS=true`。
- 对 UI 改动保留小屏尺寸 overflow 测试。
- pending timers 要通过 mock、pump、dispose 或关闭真实网络请求解决。

教训：

- 命令非零不一定代表代码没变；要看输出事实。但最终质量门仍要回到通过状态。

### 9. 管理端表格不应依赖横向滚动

历史问题：

- 用户多次反馈管理端表格横向滚动、删除按钮在页面外、内容显示不全、留白过多。

正确方式：

- 表格列要分优先级：核心字段常显，低频字段放详情弹窗。
- 操作按钮用紧凑图标/菜单，不要占满一整列。
- 移动端管理端要用卡片列表或详情抽屉，不要强行宽表。

教训：

- 管理端是高频操作界面，不要为了展示所有字段牺牲可操作性。

### 10. 用户要求“真机调试”时，不要只给理论结果

历史问题：

- 多次出现“真机预览效果”“重新安装到真机中”“正式版安装到连接的手机上”。
- 用户会直接根据真机截图反馈 UI 和功能问题。

正确方式：

- 真机调试要明确使用 debug 还是 release。
- 安装路径要从实际 build 输出取，不要假设当前目录。
- 真机结果要说明：安装是否成功、打开是否成功、验证了哪些页面、没有验证哪些页面。

教训：

- 对 App 项目，桌面构建通过只是基础，真机体验才是验收现场。

## 三、用户偏好与设计理念档案

### 1. 产品定位

- 这是只服务两个人的私有生活 App，不是公开产品。
- 目标是记录、纪念、提醒、备份、同步和陪伴。
- 不追求商业化、增长、陌生人社交、广告、复杂多租户。
- 数据安全、可恢复、稳定同步，比功能数量更重要。

### 2. UI 审美偏好

- 喜欢参考图一比一复刻，尤其是移动端页面。
- 喜欢温柔、可爱、生活化、有主题感的界面。
- 全局 App 页面风格基准：整体采用梦幻治愈的可爱风设计，以低饱和的奶油粉、浅紫和柔白色为主色调，营造轻盈、温柔、带少女感的视觉氛围。页面应大量使用圆角卡片、半透明玻璃质感和有呼吸感的留白布局，保持通透、整洁、柔和。
- 图标与装饰基准：图标要简洁软萌，优先使用 Material/Lucide/SF Symbols 这类专业图标，不使用 emoji 作为 UI 图标；可以搭配细腻的小装饰元素，如星星、爱心、爪印、柔和光点等，增强俏皮感和亲和力，但不能喧宾夺主或影响阅读。
- 信息层级基准：主标题醒目，说明文字轻柔，功能卡片排布规整有序；所有入口必须真实可点、反馈明确。整体既要实用，也要呈现温暖、甜美、轻松的产品气质，适合记录生活、情绪与日常小工具类场景。
- 主题不能只是换色，必须有对应背景、吉祥物、插图和页面氛围。
- 默认主题、蛋仔主题等需要不同吉祥物和图片资产。
- 不喜欢单调登录页、丑弹窗、原生感太重的表单。
- 通知、toast、弹窗要居中、美化、短暂展示，不要显得廉价。

### 3. 布局偏好

- 手机首页必须适配小屏，支持滚动，不能内容被截断。
- 常用信息优先：首页关注今日提醒、纪念日、最近日记、快捷入口、心情日历。
- 快捷入口不能过大，模块排列要紧凑。
- 不喜欢按钮、标题、底部导航互相遮挡。
- 管理端尽量不要出现横向滚动条。
- 管理端详情更偏好弹窗展示，不喜欢侧边展开挤压主表格。

### 4. 交互偏好

- 看起来能点的地方必须真的有效。
- 新增、删除、编辑是基础能力，不能只做列表 UI。
- 删除要有确认，已完成提醒不应继续留在状态栏。
- 状态栏点击提醒要进入对应页面并完成确认流程。
- 添加纪念日等表单不希望保存按钮突兀地从底部出现。
- 登录验证在 UI 未稳定前可以暂时关闭，但最终要恢复合理授权。

### 5. 功能偏好

- 登录只保留账号密码，短信验证、找回密码、注册暂不需要。
- 管理端要能发布公告、上传漫画、上传音乐、上传版本、查看媒体和同步数据。
- App 端需要音乐播放器接近网易云体验，歌词跟随播放进度。
- 小笨漫画由管理端上传，App 查看，每个漫画不超过 10 张图的早期设想可作为内容约束参考。
- AI 助手要懂项目上下文，最好能生成待确认动作，比如记账、提醒、日记草稿。
- 媒体和更新包下载速度重要，COS/缓存/缩略图体验要考虑。

### 6. 数据与部署理念

- 不允许无提示覆盖或丢失数据库。
- 本地数据、服务端数据、COS 数据需要解释清楚存储位置和迁移关系。
- 服务器部署可以由 Codex 操作，但必须清楚告诉用户宝塔中怎么配置。
- 生产环境改动前要备份，特别是数据库和上传目录。
- 历史敏感凭据需要轮换，后续不应再贴到对话中。

## 四、Codex 后续可直接遵循的行为准则

### 1. 默认工作流

1. 先读 README、相关 `*-ui-contract.md`、本经验文档和实际代码。
2. 明确本次是 UI、数据模型、后端 API、管理端、部署还是真机联调。
3. 对每个 UI 控件建立“控件 -> 数据/动作/API/预留文档”的映射。
4. 修改代码后运行对应验证命令。
5. 如果有未实现内容，必须更新文档，不能只在回复里口头说明。

### 2. UI 规则

- 以参考图为准时，优先保证布局层级、信息密度、图标位置和真实可用性。
- 不要做只有样式没有动作的按钮。
- 不要让文字、标题、按钮、底部导航互相遮挡。
- 不要用“横向滚动表格”解决管理端布局问题。
- 弹窗、toast、表单、上传进度属于用户强感知细节，必须认真设计。
- 主题必须包含资产差异，不只是配色差异。

### 3. 功能规则

- 新增页面必须同时考虑新增、编辑、删除、空状态、错误状态和加载状态。
- 新字段必须进入模型、序列化、同步、管理端展示和旧数据迁移。
- AI 写入真实数据前必须生成待确认动作，不能直接落库。
- 通知相关功能必须覆盖调度、点击路由、完成清理和权限失败态。
- 媒体相关功能必须覆盖上传失败、加载慢、缩略图、COS 路径和权限。

### 4. 验证规则

- Flutter 改动默认跑 `flutter analyze` 和相关 `flutter test`。
- 后端改动默认跑 `npm.cmd run build`、相关测试；发布前必须修 `npm.cmd run lint`。
- 管理端改动默认跑 `npm.cmd run build`。
- UI 改动要尽量做小屏 overflow 检查。
- 真机联调要记录安装类型、API 基址、验证页面和失败项。

### 5. 部署规则

- 远程部署前先备份数据库和上传目录。
- 不执行没有绝对路径边界的删除命令。
- 不把本地空数据库覆盖线上数据库。
- COS、数据库、宝塔、Nginx、PM2 的配置只记录变量名和位置，不记录密钥值。
- 每次服务器操作后用健康检查和日志确认，不只看命令返回。

### 6. Windows 执行规则

- PowerShell 默认使用兼容写法，不使用 `??`。
- 中文输出前设置 UTF-8。
- 搜索优先用 `rg`，但注意正则转义。
- 后台服务用 `Start-Process -WindowStyle Hidden`，并写入日志文件。
- 文件编辑用 `apply_patch`，不要用临时脚本直接改项目文件。

### 7. 安全规则

- 不在回复、文档、提交信息中回显密钥。
- 发现用户提供密钥时，只确认“已收到/请写入指定环境变量”，不要复述值。
- 历史会话已出现的密钥要提醒轮换。
- 管理端访问密码、SSH Key、COS Secret、AI Key 都按生产凭据处理。

## 五、项目默认优先级

P0：

- 数据不丢失。
- 同步不误导。
- 后端 lint/build/test 质量门。
- 登录、备份、部署、密钥安全。

P1：

- UI 控件真实可用。
- 关键页面移动端不溢出。
- 备忘、日记、情侣事项、本周目标等结构化字段闭环。
- 音乐、漫画、通知、设置的预留动作收口。

P2：

- 管理端表格体验。
- 主题资产质量。
- AI 动作助手。
- COS 性能、缩略图、下载体验。
- PostgreSQL 迁移和恢复演练。

## 六、每次完成前的自检清单

- 是否读过本文件和相关 contract？
- 是否基于实际代码，而不是基于旧文档猜测？
- 是否有 UI 控件仍是预留？若有，是否记录？
- 是否有字段只写进正文标记？若有，是否说明迁移计划？
- 是否跑了对应验证命令？
- 是否避免回显任何密钥？
- 是否保护了用户已有改动和生产数据？
- 是否用中文清楚说明完成项、失败项和下一步？
